# Documenting with Doxygen

## Overview

The API docs are generated by Doxygen from the comments in `include/` and
`src/` and published to GitHub Pages. CI runs Doxygen on every PR, but
**nothing fails on a Doxygen warning**, and some mistakes don't even warn:
a documented function can vanish from the site, or a link can silently turn
into plain text. So run Doxygen yourself and look at the result.

## The setup

| Piece | What it does |
| --- | --- |
| `docs/Doxygen` | the Doxyfile: only `PROJECT_NAME`, `INPUT` (`src include docs`), `INCLUDE_PATH`, `OUTPUT_DIRECTORY` (`docs/generated`) |
| `docs/mainpage.dox` | the start page (`\mainpage`) |
| `.github/workflows/github-pages.yaml` | `mattnotmitt/doxygen-action` runs Doxygen on every PR and push; on `main`, `peaceiris/actions-gh-pages` pushes `docs/generated/html` to the `gh-pages` branch |

Everything else is a Doxygen default. The ones that matter here:

- `EXTRACT_ALL = NO`, `EXTRACT_PRIVATE = NO`: only documented entities
  appear, private members never do.
- `JAVADOC_AUTOBRIEF = NO`: a brief needs an explicit `\brief` (or `///` on
  a single line); the first sentence is not taken automatically.
- `WARN_AS_ERROR = NO`, `WARN_NO_PARAMDOC = NO`: warnings only, and a
  function whose parameters are all undocumented doesn't warn at all.
- `RECURSIVE = NO`: only the top level of `src/`, `include/` and `docs/`,
  which matches the flat layout the Arduino IDE needs.
- `HAVE_DOT = NO`: class diagrams come from Doxygen's built-in renderer, even
  though the action installs graphviz.
- `GENERATE_LATEX = YES`: LaTeX is generated and thrown away.

The action's tag is the Doxygen version (`1.12.0` installs
`doxygen=1.12.0-r0`); Renovate bumps it like every other action.

## Running Doxygen locally

The cloud session has no `doxygen`, and the action is a Docker container.
Use the same version as CI, outside the repo:

```sh
url=https://github.com/doxygen/doxygen/releases/download
mkdir -p ~/doxygen
curl -sSL $url/Release_1_12_0/doxygen-1.12.0.linux.bin.tar.gz |
  tar xz -C ~/doxygen
```

Then run it from the repo root (the paths in the Doxyfile are relative to
it) with stricter settings appended on stdin; later lines win:

```sh
( cat docs/Doxygen
  echo "OUTPUT_DIRECTORY = $HOME/doxygen/out"
  echo "GENERATE_LATEX = NO"
  echo "WARN_NO_PARAMDOC = YES"
  echo "QUIET = YES" ) | ~/doxygen/doxygen-1.12.0/bin/doxygen -
```

- Only warnings are printed then. Compare them before and after your change;
  `main` isn't warning-free.
- Open `~/doxygen/out/html/` (or grep it) to check that what you documented
  is really there: `ls ~/doxygen/out/html | grep -E '8h\.html|^class'`.
- A plain `doxygen docs/Doxygen` writes to `docs/generated/` (gitignored),
  like CI does.

## Comment style

Match the existing headers:

```cpp
/**
 * \brief Blinks the node LED once per cycle.
 *
 * Shows that the firmware is alive: every call to blink() switches the node
 * LED on for half a cycle, then waits for the next cycle to start.
 */
class led_blinker
{
public:
  /**
   * \brief Constructor.
   *
   * \param cycle_duration The duration of one blink cycle in milliseconds.
   */
  explicit led_blinker(int cycle_duration);

  /// The type \c millis() returns.
  using millis_t = unsigned long;
};
```

- `/** … */` blocks with backslash commands (`\brief`, `\param`, `\return`,
  `\c`, `\warning`, `\parblock`), not `@brief` or `//!`. `///` only for a
  one-line brief.
- Document in the header, where users of the class read it. A comment on the
  definition in the `.cpp` is merged in after the header's (both are shown),
  so keep implementation notes there and the contract in the header.
- `\c name` for code in prose, `\p name` for a parameter of the function
  being documented. `name()` and `class_name::method()` auto-link when the
  target exists.
- New code uses `lower_snake_case` (issue #157), in the comments too.

## What to write

The signature already says the types. The comment says what it doesn't:

- **Units and ranges**: milliseconds, GPIO numbers, what `0` or a negative
  value means.
- **Blocking**: whether a call returns at once or waits (`delay()`), and for
  how long. On the ESP8266 that decides whether the WiFi stack starves.
- **Lifetimes and ownership**: who keeps a pointer and how long the object
  must live, like the `WifiDependent`s that `WifiConnection` keeps.
- **When callbacks run**: from which context (`loop()`, a WiFi event
  handler, a `Ticker`) and in which order.
- **`DEBUG`-only behavior**: what changes with `-D DEBUG`.

Describe what the code does, not what it should do. Don't invent behavior
the code doesn't have; if the comment and the code disagree, say so to the
user instead of picking one.

## Pitfalls

Each of these was checked with Doxygen 1.12.0:

- **A header without a `\file` comment hides its free functions, macros and
  constants**, documented or not, and without a warning (`debug.h` and
  `led.h` on `main`). A class in such a header still shows up. Give such
  headers a file comment:

  ```cpp
  /**
   * \file
   * \brief Serial logging that compiles away without \c DEBUG.
   */
  ```

- **A link to a member that doesn't exist is plain text, no warning.**
  After a rename, `wifi_dependent::on_lost()` in a comment silently stops
  linking. Grep the comments for the old names, and check the links in the
  output.
- **`\param` names must match the definition's names.** A comment on the
  `.cpp` definition is checked against the `.cpp` parameter names, so a
  rename on one side warns (`argument 'x' of command @param is not found`).
- **Plurals of class names**: `\c WifiDependent s` leaves a gap in the
  output; `\ref WifiDependent "WifiDependents"` links with the right text.
- **`\brief` on a line of its own**, then a blank comment line, then the
  details. Stray `*` (`\brief Constructor.  *`) end up in the output.
- A new folder under `src/` or `include/` isn't scanned (`RECURSIVE = NO`),
  and isn't allowed anyway (Arduino IDE).

## Changing the setup

- A Doxyfile option goes into `docs/Doxygen`, nowhere else; the action has
  no inputs for options. Look options up in the
  [configuration reference](https://www.doxygen.nl/manual/config.html) for
  the version CI uses.
- Making warnings fail CI (`WARN_AS_ERROR = FAIL_ON_WARNINGS`) only works
  once `main` has none.
- The site is deployed from `main` only. A PR shows nothing on Pages; its
  workflow run only proves that Doxygen ran.

## Before pushing

- [ ] Doxygen 1.12.0 run locally, no new warnings
- [ ] What you documented is in the HTML (headers with free functions or
      macros have `\file`)
- [ ] Links to renamed or removed members updated
- [ ] Units, blocking and lifetimes stated where they apply
